# Chapter 7 — DID, AT Protocol and ActivityPub: references

Every standard this chapter's implementation reads, with what it is used for
and which module uses it — plus, in their own group, the standards a compliant
implementation would need for the namespaces this one refuses. Where a row says
*not implemented* or *cited for the deviation*, the row says so.

## Naming and identifiers

| Identifier | Title | Used for |
|---|---|---|

| [did:web Method Specification](https://w3c-ccg.github.io/did-method-web/) | did:web Method Specification, W3C Credentials Community Group draft | §5.3 the read algorithm quoted and implemented in full — `:` → `/` before percent-decoding, the `%3A` port, `.well-known` only for a bare host, then `did.json` — and checked against the specification's published examples. §9.3 the same structure read as a **canonicalisation** rule for a binding subject: first segment a domain with an optional percent-encoded port, the rest **path** segments whose case is significant because a URL path's is. A Community Group draft, not a W3C Recommendation: it is the only written definition of the method and it is not ratified. — `src/did-protocol.js` (`didWebUrl`), imported by `src/bsky.js` so the PDS lookup reads the method the same way (§6.2); `src/receipt.js` (`canonicalAtprotoDid`) |
| [did:plc Method Specification v0.1](https://web.plc.directory/spec/v0.1/did-plc) | did:plc — Public Ledger of Credentials, v0.1 ([source](https://github.com/did-method-plc/did-method-plc)) | §5.2 the directory endpoint `GET /<did>` that returns the current document — the whole of what is *resolved* with. §9.3 also the identifier's shape — 24 base32 characters of a truncated hash — which is the admissibility rule for a binding subject (`../../DEVIATIONS.md` DI-14). The parts *not* used are what make the method verifiable: the identifier is a truncated hash of the signed genesis operation, and `GET /<did>/log/audit` publishes the signed operation log (`../../DEVIATIONS.md` DI-2). One operator's specification, versioned v0.1. — `src/did-protocol.js`, `src/bsky.js` |
| [W3C DID Specification Registries](https://www.w3.org/TR/did-spec-registries/) | DID Specification Registries, W3C Group Note | §5.1 where a method name is looked up. | [RFC 9498](https://www.rfc-editor.org/rfc/rfc9498) | The GNU Name System | §3 namespace precedence — resolve in the alternative namespace when its suffix matches, and do not continue into DNS on failure. §9.10 is the only place this rule is written down in an RFC; `../../SPEC.md` adopts it and this chapter inherits it. — `../../src/router.js` |
| [WHATWG URL Standard](https://url.spec.whatwg.org/) | URL Standard — [host parsing](https://url.spec.whatwg.org/#host-parsing) | §3.1 the reason `did:` must not be a *standard* scheme: a standard scheme's authority is lowercased, IDNA-mapped and, when the last label is all digits, parsed as IPv4, while a method-specific identifier is byte-sensitive. Also why the canonical `at://did:plc:…` AT-URI does not parse and must be dispatched by scheme prefix. — `../../src/router.js`; the browser's `src/main.cjs` (not extracted) |

## The local methods, and the key material they carry

These are read by `src/did-local.js` alone: the three methods whose document is
derived from the identifier (SPEC §5.1), and the standards that decide whether
the key inside one is real (SPEC §5.1a). A key that any of these refuses is a
**400** here, not a document (`../../DEVIATIONS.md` DI-12).

| Identifier | Title | Used for |
|---|---|---|
| [did:key Method Specification](https://w3c-ccg.github.io/did-method-key/) | did:key Method Specification, W3C Credentials Community Group draft | §5.1 the identifier form — base58btc multibase over a multicodec-prefixed public key — and the `Multikey` document derived from it, including that an X25519 key lists `keyAgreement` only. §5.1a the admitted key types and their fixed lengths. — `src/did-local.js` (`didKeyDocument`, `KEY_CODECS`) |
| [did:jwk Method Specification](https://github.com/quartzjer/did-jwk/blob/main/spec.md) | did:jwk Method Specification | §5.1 the identifier form — base64url of a JWK — the `JsonWebKey2020` verification method, and the rule that maps `use` to the verification relationships listed (`enc` → `keyAgreement` only, `sig` → everything else, absent → all). §5.1a the method's unpadded base64url encoding, which this implementation additionally requires to round-trip exactly. **Its printed P-256 example is not a point on P-256**, so the chapter's vector is a valid key of the same shape rather than that one (`../tests/did-local.test.js`). — `src/did-local.js` (`didJwkDocument`) |
| [did:pkh Method Specification](https://github.com/w3c-ccg/did-pkh/blob/main/did-pkh-method-draft.md) | did:pkh Method Specification, W3C Credentials Community Group draft | §5.1 a blockchain account as an identifier, and the verification-method type each namespace fixes — `EcdsaSecp256k1RecoveryMethod2020` for `eip155`/`bip122`, `Ed25519VerificationKey2018` for `solana`/`tezos` — with `blockchainAccountId` carrying the CAIP-10 account. — `src/did-local.js` (`didPkhDocument`, `PKH`) |
| [CAIP-2](https://chainagnostic.org/CAIPs/caip-2) / [CAIP-10](https://chainagnostic.org/CAIPs/caip-10) | Blockchain ID and Account ID specification | §5.1 the `<namespace>:<reference>:<address>` grammar a `did:pkh` identifier must satisfy, and the namespace set this implementation admits. An address that does not match its namespace's syntax is refused. — `src/did-local.js` |
| [multicodec](https://github.com/multiformats/multicodec) | Multiformats — multicodec table | §5.1a the unsigned-varint key-type prefixes (`0xed` Ed25519, `0xec` X25519, `0xe7` secp256k1, `0x1200`–`0x1202` the NIST curves, `0x1205` RSA), read **canonically**: a trailing-zero continuation byte and a fifth byte above `0x0f` are both refused, so one key has one spelling. — `src/did-local.js` (`readVarint`) |
| [RFC 4648](https://www.rfc-editor.org/rfc/rfc4648) | The Base16, Base32, and Base64 Data Encodings | §5.1a §5 base64url **without padding**, required to re-encode to the input byte for byte — for the `did:jwk` identifier itself and for every JWK member read out of it, so no second encoding of a key resolves. — `src/did-local.js` (`base64urlBytes`) |
| [RFC 7517](https://www.rfc-editor.org/rfc/rfc7517) | JSON Web Key (JWK) | §5.1a the JWK object, its `kty`, and §4.2 the `use` member with its registered values `sig` and `enc` — an unknown `use` is refused rather than ignored, because `use` decides which verification relationships the document lists. Also the private members (`d`, `p`, `q`, `dp`, `dq`, `qi`, `k`) whose presence makes an identifier a leak. — `src/did-local.js` (`validateJwk`, `didJwkDocument`) |
| [RFC 7518](https://www.rfc-editor.org/rfc/rfc7518) | JSON Web Algorithms (JWA) | §5.1a §6.2 the `EC` key type, its curve names and the fixed octet length of `x` and `y` for each (P-256 32, P-384 48, P-521 66); §6.3 the `RSA` key's `n` and `e`. — `src/did-local.js` (`validateJwk`) |
| [RFC 8037](https://www.rfc-editor.org/rfc/rfc8037) | CFRG ECDH and Signatures in JOSE | §5.1a the `OKP` key type with `crv` of `Ed25519` (signing) or `X25519` (key agreement) and a 32-octet `x` — and the reason a curve and a `use` that disagree are refused: the curve fixes what the key can be used for. — `src/did-local.js` (`validateJwk`, `validateOkp`) |
| [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032) | Edwards-Curve Digital Signature Algorithm (EdDSA) | §5.1a §5.1.7's subgroup requirement, read as a check on the key: an Ed25519 public key must decode to a valid point that is **not small-order and is torsion-free**, or a signature verification against it does not mean what it appears to. — `src/did-local.js` (`validateOkp`) via `@noble/curves` |
| [RFC 7748](https://www.rfc-editor.org/rfc/rfc7748) | Elliptic Curves for Security (Curve25519, Curve448) | §5.1a §6.1's low-order points: an X25519 public key is probed with a public, deterministic X25519 computation that rejects them. It is a well-formedness check and **not** a possession proof — no user secret and no network are involved (DI-12). — `src/did-local.js` (`validateOkp`) via `@noble/curves` |
| [RFC 8017](https://www.rfc-editor.org/rfc/rfc8017) | PKCS #1 v2.2 | §5.1a `RSAPublicKey ::= SEQUENCE { modulus INTEGER, publicExponent INTEGER }` — the DER a `did:key` RSA identifier carries. The key must import as that, and **re-export to exactly the same bytes**, so no alternative encoding of one modulus is a second DID; the modulus and exponent are then bounded and checked odd, with `3 <= e < n`. — `src/did-local.js` (`didKeyDocument`, `validateJwk`) |

| Identifier | Title | Used for |
|---|---|---|
| [atproto.com/specs/handle](https://atproto.com/specs/handle) | AT Protocol — Handle Resolution | §6.1 the two authoritative handle→DID methods (`_atproto.<handle>` DNS `TXT` `did=…`, and `GET https://<handle>/.well-known/atproto-did`) and the bidirectional-verification requirement against `alsoKnownAs`. **Neither method is implemented**; the public AppView is asked instead (`../../DEVIATIONS.md` DI-5). | [atproto.com/specs/xrpc](https://atproto.com/specs/xrpc) | AT Protocol — XRPC | §6.1 the HTTP+JSON transport: `GET|POST /xrpc/<nsid>`, query parameters, `Bearer` auth, and the error body shape (`error`, `message`) mapped to a typed error. | [atproto.com/specs/repository](https://atproto.com/specs/repository) | AT Protocol — Repository | §6.3 and §10.5 the signed commit over a Merkle Search Tree, verified with the `#atproto` key from the account's DID document, that would make an `at://` record *resolved* rather than *fetched*. **Not implemented**; cited as the bar. — no module |
| [public.api.bsky.app](https://docs.bsky.app/) | Bluesky public AppView | §6.1 the unauthenticated read service used for `com.atproto.identity.resolveHandle` and for profile and feed reads. Not a standard; listed because a load-bearing dependency belongs in the references. — `src/bsky.js`, `src/xrpc.js` |

proposed standard, and their formats may change. These are the standards they
are built from.

## Cited for what a compliant implementation must do — not read by this code

The `at` and `activitypub` namespaces are fail-closed (SPEC §7, §8). Their
refusal pages name what resolving them would require and §10.5 turns that into
a bar. These are the standards that bar is made of; no module in `src/`
imports, fetches or parses any of them.

| Identifier | Title | Used for |
|---|---|---|
| [RFC 7033](https://www.rfc-editor.org/rfc/rfc7033) | WebFinger | §7 `GET https://<host>/.well-known/webfinger?resource=acct:<user>@<host>` and the `self` link with type `application/activity+json` that names the actor URL — and what it is *not*: a redirection published by the host, never an authentication of the actor it points at. — no module |
| [W3C ActivityPub](https://www.w3.org/TR/activitypub/) | ActivityPub, W3C Recommendation 23 January 2018 | §7, §10.5 the actor object and the client's side of the protocol. ActivityPub specifies no client-side authentication of a fetched object; HTTP Signatures authenticate server-to-server delivery, and an implementation must not borrow the latter to imply the former. — no module |
| [W3C ActivityStreams 2.0](https://www.w3.org/TR/activitystreams-core/) | Activity Streams 2.0 Core | §7 the object vocabulary an actor document is written in. — no module |
| [W3C Controller Documents](https://www.w3.org/TR/controller-document/) | Controller Documents 1.0 (Multikey) | §10.5 the `verificationMethod` form (`#atproto`, type `Multikey`) an AT Protocol DID document carries, which a record-signature check would read the key from.
